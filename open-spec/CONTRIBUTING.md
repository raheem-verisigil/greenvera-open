# Contributing

Include a problem statement, affected use cases, proposed schema/protocol change, realistic JSON example, compatibility analysis, privacy/security considerations and conformance tests.

Do not silently repurpose fields. Breaking changes require a major schema version and migration notes. Prefer additive optional fields and explicit extension namespaces.

Never conflate supplier declarations, documentary records, automated checks, expert assessments and independent assurance. Preserve issuer, scope, date, method, uncertainty and limitations.

Do not publish credentials, customer evidence or exploitable vulnerabilities in public issues. Use GitHub's private vulnerability reporting channel. A proposal is not part of the specification until explicitly accepted and versioned.
